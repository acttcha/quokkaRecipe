# 레시피 생성 평가

`supabase/functions/gemini-proxy/prompt.ts` 를 고친 뒤 품질을 숫자로 확인하는 도구.
실제 gemini-proxy 를 호출하므로 **배포된 버전**을 잰다(1회 약 2원).

```bash
node scripts/recipe-eval/eval.js <라벨> [독립횟수=4] [연속횟수=4]   # 새 방식(recipeInput)
LEGACY=1 node scripts/recipe-eval/eval.js <라벨>                     # 1.0.5 앱이 보내는 형식
ONLY=A,D node scripts/recipe-eval/eval.js <라벨>                     # 일부 세트만
```

세트: A 한식 / B 닭가슴살 / C 양식 / D 계란 알레르기 / E 채식 / F 비건.
지표: 목록 밖 재료(환각) · 알레르기·식단 위반 · 연속 호출 반복 · 에러 · 원가 · 지연.

2026-10-30 기준선(v12): 두 경로 모두 환각 0/84, 위반 0, 반복 0, 에러 0/42, 약 2.7원, 4.2초.

## 품질(레시피로서 쓸 만한가)

```bash
LEGACY=1 node scripts/recipe-eval/sample.js <라벨> [세트당 호출수=3]
```

eval.js 와 겹치지 않는 냉장고 6종(G~L)으로 레시피 전문을 out/sample_<라벨>.json 에 저장하고,
간(소금·후추·된장 과다, 짠 재료에 소금 추가)·반죽 없는 전·영어 조리시간·괄호 이름·마늘 먼저 볶기를 자동 점검한다.
자동 점검은 보조일 뿐이라 **전문을 직접 읽고** 판단할 것.

| 라운드 | 문제 레시피 | 주요 유형 |
|---|---|---|
| q1 양념 좁음 | 21/36 | 영어 조리시간 18, 마늘 순서 4, 짠 간 3 · 닭볶음탕이 고추장 없는 찜닭 |
| q2 양념 확대 | 17/36 | 후추 1작은술 6, 반죽 없는 전 3, 된장 과다 2 |
| q3 간 기준 | 5/48 | 마늘 순서 4, 된장 과다 1 |
| q4 (현재) | 3/48 | 마늘 순서 3 |

배포 직후 차가운 인스턴스에 동시 요청이 몰리면 `BOOT_ERROR` 가 나는데 코드 문제가 아니다.
스크립트가 시작 전에 데우지만, 배포 직후라면 30초쯤 두고 돌리는 게 안전하다.

테스트 지갑 정리(Supabase SQL Editor):
```sql
delete from usage_events where user_id like 'prompt_test_%' or user_id = 'probe';
delete from wallets      where user_id like 'prompt_test_%' or user_id = 'probe';
```

## 페르소나(셰프 쿼카)별
`LEGACY=1 node scripts/recipe-eval/persona.js <라벨> [반복=3]` — 14개 페르소나 × 냉장고 2개(P1 닭가슴살·두부…, P2 돼지고기·김치·고구마…).
후보 단계만 보려면 `node scripts/recipe-eval/stage1.js <페르소나id>` (후보별 적합도 f 출력).

| 페르소나 | p2 (적합도 없음) | p6 (적합도 기준+서버 강등+본문 기준) |
|---|---|---|
| 다이어트 | 김치찌개·바나나 우유 등 섞임, 단맛 33% | 찜·국·라페 위주, 208kcal, 단맛 8% |
| 디저트 | 디저트 비율 낮음, 짠 요리 섞임 | 단맛 100%, 짠 요리 0 |
| 세계요리 | 한식 다수 | 한식 8% |
| 미슐랭 | 일반 반찬 | 한식 25%, 플레이팅 단계 포함 |
| 도시락 | 국·찌개 섞임 | 국물 0%, 마지막 단계에 보관법 |
| 키토 | 탄수 재료 58% | 탄수 재료 0%, 탄수 6g |
| 벌크업 | 단백 27g | 단백 34g |
| 매운맛 / 순한맛 / 비건 | 92% / 매운 0 / 동물성 0 | 유지 |

구조: 1단계 f(0~2)를 `PERSONA_FIT_RULES` 로 판정 → 서버가 이름으로 확실한 것은 0점(`PERSONA_DEMOTE`, 디저트 외 음료) →
적합도 높은 순으로 선택 → 2단계에 `PERSONA_DETAIL_RULES`(기름·당·단백 수치, 플레이팅, 보관법).

## 알레르기·맵기
`node scripts/recipe-eval/allergy.js <라벨> [반복=4]` — 앱 선택지 그대로(유제품·해산물·견과류·글루텐·계란·돼지고기, 영어 dairy·eggs),
맵기 "전혀 못 먹음"/"약간만", 요리명 검색(새우볶음밥·크림 파스타·김치전·멸치볶음 + 알레르기). `ONLY=세트명,…` 으로 일부만.

알레르기는 3겹:
1. 입력 — 앱 값은 분류명이라 `ALLERGY_GROUPS` 로 실제 재료명(우유·버터·새우·굴소스·땅콩·국수…)으로 펼쳐 재료·양념·후보에서 뺀다.
2. 생성 — `allergyNote` 로 펼친 목록을 첫 호출부터 알려준다("해산물"만 주면 굴소스·액젓을 넣었다).
3. 출력 — `findViolations` 가 완성된 레시피(재료 목록 엄격, 조리 단계는 실제 재료명만)를 다시 본다. 걸리면 1회 재생성,
   그래도 걸리면 그 레시피를 빼고, 하나도 안 남으면 잎사귀 환불 + 안내 문구. 요리명 검색도 이 검사를 받는다.
   "버터 대신", "젓갈이 없는지 확인하세요", "글루텐프리 간장", "두유 크림" 은 위반이 아니다. 응답 헤더 `x-allergy-guard` 로 개입 내역 확인.

맵기는 금지하지 않고 양으로 조절(`spiceLimit`): 전혀 못 먹음 = 2인분 고춧가루 ½작은술·고추장 ½큰술 이하 + 고추가 주인공인 요리 후순위,
약간만 = 고춧가루 1작은술·고추장 1큰술 이하. 청양고추·불닭만 금지.

기준선 a10: 위반 0/128 (분류명 펼치기 전엔 "유제품" 으로 우유·버터를 못 걸렀고, 요리명 검색은 서버 검사 자체가 없었음).
